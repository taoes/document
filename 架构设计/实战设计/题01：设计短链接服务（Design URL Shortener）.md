下面我以“资深架构师面试官”的视角来拆解这道题：先给出我期望候选人回答的参考设计方案，再给出我会继续追问的问题。重点不是背答案，而是看候选人能否抓住 **读多写少、唯一短码、分片路由、热点、异步计数、降级、安全** 这几个核心矛盾。

## 一、面试官评估框架

  

我会重点看这几项：


1. **需求澄清与容量估算**：是否先问 QPS、存储年限、一致性、过期、统计精度、可用性。
2. **读写分离**：写少读多，读路径必须极短，不能每次查 DB。
3. **短码唯一性与可扩展性**：自增、随机、哈希如何取舍。
4. **分片与路由**：短码如何作为分片键，读时如何一次定位。
5. **缓存与热点**：多级缓存、穿透/击穿/雪崩、热点 key。
6. **异步计数**：不能每次点击写 DB。
7. **降级容灾**：DB、Redis、Kafka 故障时重定向还能不能保住。
8. **安全风控**：恶意链接、刷点击、开放重定向。

## 二、面试官参考设计方案

### 1. 需求与容量估算

- 写：每日千万级，平均约 `1000万 / 86400 ≈ 116 QPS`，峰值按 5~10 倍，约 `500~1200 QPS`。
- 读：`10万 QPS`，峰值可能 `20万 QPS`，典型读多写少。
- 短码长度：Base62 下，6 位约 `568亿`，7 位约 `3.5万亿`。每天 1000 万，6 位约可用 15 年，7 位更稳。
- 存储：一年约 36.5 亿条，按 1KB 估算约 36.5TB，必须分片。
- 一致性：短链映射要求强一致或最终一致？点击统计允许最终一致。重定向要求高可用、低延迟。

> $15 年 = {62^6}\div({10000000 * 365})$
> $964 年 = {62^7}\div({10000000 * 365})$

### 2. 整体架构与核心模块

```text
-> DNS / LB / API 网关 / WAF
	-> 写服务：生成短链
	-> 发号器 / 短码服务
	-> DB 分片
	-> 可选：Kafka 异步审核、统计

-> 读服务 / 重定向服务
	-> 本地缓存 -> Redis 集群 -> DB 分片
	-> 302 重定向
	-> Kafka 发送点击事件

-> 统计层：Kafka -> Flink -> Redis / ClickHouse
-> 风控审核：黑名单、Safe Browsing、配额、限流
-> 监控降级：配置中心、熔断、限流、只读开关
```

  核心模块：

- 接入层：LB、API Gateway、WAF、限流。
- 写服务：创建短链、校验、发号、落库。
- 读/重定向服务：查缓存、302、发点击事件。
- 短码服务/发号器：全局唯一 ID 或随机短码。
- 存储层：MySQL 分库分表 / TiDB / HBase / Cassandra。
- 缓存层：Redis 集群 + 本地缓存。
- 统计层：Kafka + Flink + Redis/ClickHouse。
- 风控审核：恶意 URL 检测、爬虫识别。
- 运维层：监控、降级、容灾。

### 3. 短码生成方案

我会期望候选人对比三种方案：

| 方案             | 优点        | 缺点           |
| -------------- | --------- | ------------ |
| 自增 ID + Base62 | 无冲突、短、可控  | 可被枚举，依赖发号器   |
| 随机字符串          | 不可预测      | 有冲突，需重试，写放大  |
| 长 URL 哈希       | 同 URL 可复用 | 哈希冲突，截断后冲突更高 |
|                |           |              |

  

推荐方案：

- 使用 **全局发号器 + Base62**：如 DB 号段、Redis INCR、Snowflake、Leaf。
- 对 ID 做混淆，如 Feistel 加密、XOR 盐，避免连续可枚举。
- 自定义短码走独立唯一索引，冲突则拒绝或重试。
- 随机短码用 `SETNX` 或 DB 唯一索引，冲突重试。
- 冲突处理：唯一索引兜底，重试有限次；高并发下可预生成短码池。


### 4. 数据库分片与主键设计

- 分片键：`short_code`，因为读请求天然按短码查。
- 路由：`hash(short_code) % N` 或一致性哈希，读时一次定位。
- 表结构示例：

```sql
create table short_url(
	short_code varchar(8) primary key,
	long_url text,
	created_at timestamp,
	expire_at timestamp null,
	user_id bigint,
	status tinyint
)
```

  

- 如果使用自增 ID 生成短码，则先发号，再 Base62 得到 short_code，再按 short_code 分片写入。
- 过期：逻辑过期 + 异步清理；查询时判断 `expire_at`，过期返回 410。
- 存储选型：MySQL 分库分表适合强一致；HBase/Cassandra 适合海量 KV；TiDB 可简化分片。

### 5. 缓存层设计
读路径：
```text
本地缓存 Caffeine -> Redis 集群 -> DB 分片
```

缓存内容：
- `short_code -> long_url, expire_at, status`
- 空值缓存：`short_code -> NULL`，TTL 60s。
- 布隆过滤器：拦截不存在的短码，防缓存穿透。
- 互斥锁/单飞：防热点 key 击穿。
- TTL 加随机：防雪崩。
- 写后删缓存：短链基本不变，写 DB 后删除缓存即可。

  

### 6. 热点短链接处理

  

营销活动短链可能瞬间海量访问：

- 本地缓存保存极热短码，减少 Redis 压力。
- Redis 多副本、读写分离，热点 key 可打散或加副本。
- CDN/边缘节点做 302 重定向，尤其全国/全球活动。
- 热点探测：按 QPS 自动识别，推送到本地/边缘。
- 限流与排队：保护后端，非核心请求降级。
- 预加载：活动前把短码推送到缓存和边缘。

  

### 7. 点击量统计

  

不能每次点击写 DB。推荐：

```text
重定向服务 -> Kafka -> Flink 聚合 -> Redis / ClickHouse
```

- 重定向服务只发异步事件，不阻塞 302。
- Kafka 缓冲峰值，Flink 做窗口聚合。
- Redis 存实时计数，ClickHouse/Druid 存明细和报表。
- UV 可用 HyperLogLog 近似去重。
- 点击统计允许最终一致，防刷过滤在风控层完成。
- Kafka 不可用时，本地内存缓冲 + 采样降级。

### 8. 降级方案

- DB 宕机：本地缓存 + Redis 仍可扛大部分重定向；未命中返回 503/404；切换只读。
- Redis 宕机：本地缓存 + DB 限流兜底。
- Kafka 宕机：点击统计本地缓冲或采样，不影响重定向。
- 写服务降级：短链生成限流、排队或暂停，优先保读。
- 多机房：异地多活、主从、副本，读服务无状态可快速扩容。

  

### 9. 安全问题

- 恶意链接：黑名单、白名单、Google Safe Browsing、域名信誉、人工审核。
- 开放重定向：校验协议，禁止 `javascript:`、`data:`，限制跳转域名。
- 短码不可枚举：混淆 ID，防遍历。
- 爬虫刷点击：IP/设备指纹限流、验证码、UA/Referer 分析、去重窗口。
- 用户配额：实名、频率限制、举报机制。
- 302 而非 301：便于统计、风控和动态调整。

## 三、面试官可能追问的问题

  

我会根据候选人回答继续深挖：


1. 短码长度怎么算？6 位够不够？为什么选 Base62？
> Base62 下 6 位约 568 亿，7 位约 3.5 万亿；每日千万级，6 位约 15 年，7 位更稳。选 Base62 是因字符集大、URL 安全、短

2. 自增 ID 发号器单点怎么办？Snowflake 时钟回拨怎么处理？
> 用多实例号段、Leaf、Redis 集群发号。Snowflake 时钟回拨：等待、报警、备用 ID、逻辑时钟。

3. 随机短码冲突概率多大？冲突后重试几次？如何避免写放大？
>  量级越大冲突越高；唯一索引兜底，重试 2~3 次；预生成短码池避免写放大。

4. 同一个长 URL 是否复用短码？复用有什么问题？
> 可复用，省空间；但会影响用户统计、过期、自定义短码，通常默认不复用。

5. 数据库按什么分片？为什么不用 user_id 分片？
> 按 `short_code` 哈希分片，读时一次定位；不用 `user_id`，因为重定向只带短码，按用户会跨分片。


6. 分片后如何按短码查询？跨分片怎么处理？
> `hash(short_code)` 直接路由；跨分片查询很少，需全局索引或避免。


7. 缓存和 DB 一致性怎么保证？写后删缓存失败怎么办？
> Cache Aside，写 DB 后删缓存；删失败重试或消息补偿，TTL 兜底。

8. 缓存穿透、击穿、雪崩分别怎么解决？
> 穿透用布隆+空值；击穿用互斥/单飞；雪崩用随机 TTL+多级缓存+限流+Redis 集群高可用。

9. 热点 key 怎么发现？本地缓存和 Redis 不一致怎么办？
> 监控 QPS 自动探测，推本地/边缘缓存；不一致靠短 TTL、版本号、主动推送

10. 点击量要精确还是近似？Kafka 丢消息怎么办？
> 允许最终一致、近似精确；Kafka 丢消息用本地缓冲、重试、幂等、采样降级。

11. DB 宕机时，未命中缓存的短链怎么办？
> 返回 503/404，或读副本/备用存储兜底；优先保缓存命中。

12. Redis 也宕机了，重定向还能不能保住？
> 本地缓存+DB 限流兜底；全挂无法完全保证，需多级副本、多活。

13. 过期短链是物理删除还是逻辑删除？如何清理？
> 逻辑删除，查询判断 `expire_at`；异步清理归档，低峰物理删除。

14. 为什么用 302 不用 301？对统计和 SEO 有什么影响？
> 302 便于统计、风控、改目标；301 会被浏览器缓存，统计丢失，SEO 权重转移。

15. 恶意链接如何实时拦截？误杀怎么办？
> 黑名单、Safe Browsing、域名信誉、异步审核；误杀靠申诉、人工复核、白名单。

16. 爬虫刷点击如何识别？如何保证统计不崩？
> IP/设备/UA 限流、去重窗口、验证码、风控规则；Kafka 削峰，Flink 过滤，不影响重定向。

17. 自定义短码冲突怎么处理？
> 唯一索引兜底，冲突返回错误或建议；可加用户前缀隔离。

18. 多地域部署怎么做？数据合规怎么考虑？
> GSLB 就近接入，多机房多活，读本地写主/双写；数据本地化，跨境脱敏和合规审批。

19. 如何压测 10 万 QPS？瓶颈会在哪？
> 全链路压测、逐步加压、影子流量；瓶颈常在 Redis、DB 分片、带宽、Kafka、DNS。


20. 监控哪些指标？SLO 怎么定？降级开关如何设计？
> 看 QPS、P99、错误率、缓存命中、DB 连接、Kafka lag；SLO 如重定向 P99<50ms、可用性 99.99%；降级开关分级可回滚。

## 四、面试官眼中的加分项与红旗

  

**加分项：**

- 先澄清需求，再算容量。
- 明确读写分离、多级缓存、异步计数。
- 短码唯一性和分片路由讲清楚。
- 热点、降级、安全都有方案。
- 能说出取舍：强一致 vs 最终一致，成本 vs 可用性。

**红旗：**

- 一上来就随机字符串，不考虑冲突和重试。
- 每次点击写 DB。
- 没有分片和缓存设计。
- 热点短链没有本地缓存/边缘方案。
- DB 宕机就完全不可用。
- 忽略恶意链接和刷点击。

### base62转换编码

```python
BASE62 = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz"

def encode(num):
    if num == 0:
        return BASE62[0]
    chars = []
    while num > 0:
        num, rem = divmod(num, 62)
        chars.append(BASE62[rem])
    return ''.join(reversed(chars))

def pad(code, length):
    return BASE62[0] * (length - len(code)) + code

code = encode(100001)        # "Q0v"
print(pad(code, 6))          # "000Q0v"
print(pad(code, 7))          # "0000Q0v"
```
