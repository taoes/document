# 2026 AI Agent 开发工程师面试题（含参考答案）

> 面向后端/大模型应用开发，侧重 **LangChain、LangGraph、RAG、Agent 原理、工具调用、向量库、工程落地、故障排查**，适合Java/Python后端转Agent、AI应用开发岗位。 难度：中高级，面试口述版，精简好背。

## 一、基础概念题

### 1. 什么是AI Agent？Agent 和普通大模型对话接口的核心区别？

**答案** AI Agent 是具备**感知、思考、决策、调用工具、迭代执行**能力的智能体。不只是单纯根据prompt输出文本，能自主拆解任务、判断是否需要调用外部工具，循环执行直到任务完成。

区别：

- 普通LLM：输入prompt → 一次性输出，无状态、不会主动调用外部能力，无法处理多步骤复杂任务；
- Agent：有**规划（Plan）→ 工具调用（Act）→ 观察（Observe）→ 反思**循环，可访问外部系统、数据库、API，支持多轮迭代，具备任务闭环能力。

经典范式：ReAct（Reason + Act）是最主流的Agent基础框架。

### 2. ReAct 原理是什么？为什么ReAct比单纯CoT效果更好？

**答案** ReAct = Reason（推理思考） + Act（行动调用工具）。 执行循环：

1. Thought：思考当前任务还缺少什么信息；
2. Action：选择工具、构造参数调用外部工具；
3. Observation：拿到工具返回结果；
4. 回到Thought继续推理，直到任务完成。

CoT只在模型内部做推理，没有外部信息，容易产生幻觉； ReAct把**推理和外部工具调用结合**，模型可以用真实外部结果辅助推理，减少幻觉，适合需要事实查询的任务。

### 3. 简述 Agent 的几个核心组件

**答案**

1. **LLM大脑**：负责思考、决策、生成工具调用参数；
2. **Prompt / System Prompt**：定义Agent角色、能力、工具描述、输出格式；
3. **Tools（工具）**：API、数据库查询、计算器、代码解释器、RAG检索器等外部能力；
4. **记忆 Memory**：短期对话记忆、长期向量记忆，保存上下文；
5. **规划器 Planner**：复杂任务拆解成子任务；
6. **状态管理 / 执行器**：维护Agent执行状态，循环调度（LangGraph核心）；
7. **输出解析器 Output Parser**：解析模型输出，提取工具调用参数，处理格式异常。

### 4. Agent Memory 有哪些分类？各自适用场景

**答案**

1. **ConversationBufferMemory**：完整保存全部对话，简单；缺点上下文容易超长，token膨胀。适合短对话。
2. **ConversationSummaryMemory**：自动对历史做摘要压缩，减少token。适合长会话。
3. **ConversationBufferWindowMemory**：只保留最近N轮对话，滑动窗口。适合有轮次限制场景。
4. **VectorStoreMemory（向量记忆）**：把历史对话向量化存入向量库，做语义检索。适合长期记忆，跨会话召回历史信息。
5. **Entity Memory**：抽取实体信息（人名、订单号）单独存储。适合业务知识库。

> 面试加分点：Memory 不是必须全部塞给LLM，可以用**检索召回**替代全量上下文，控制token成本。

## 二、框架相关（LangChain / LangGraph 高频）

### 5. LangChain 和 LangGraph 的区别？什么时候用LangGraph？

**答案** LangChain：偏向组件化工具封装（Chain、Tool、Prompt），早期Agent是简单顺序链，**很难实现复杂分支、循环、多轮带状态的Agent**。适合简单RAG、单链任务。

LangGraph：LangChain生态的**状态图框架**，基于有向图，节点可以是LLM、工具调用；边可以做条件分支。核心是**状态持久化、循环、分支、断点**。

适用场景：

- 需要多轮循环思考的Agent；
- 任务存在分支判断（比如检索不到文档就走API查询）；
- 需要人工介入（Human-in-the-loop，人工审批工具调用）；
- 需要保存执行快照，支持断点恢复。

> 一句话总结：LangChain 做组件，LangGraph 编排Agent的执行流程。

### 6. 什么是 Chain？RAG Chain 执行流程

**答案** Chain：LangChain里把多个组件串联起来的执行单元，输入经过多个组件依次处理得到输出。

基础RAG Chain流程： 用户Query → Query改写/扩写 → 向量库检索TopK文档 → 文档内容拼接进Prompt → LLM基于检索结果回答。

### 7. LangGraph State是什么？怎么设计Agent State？

**答案** State是LangGraph全局状态，在图节点之间传递数据，是一个可自定义的结构体。 每次节点执行会读取、修改State，图流转依赖State。

Agent State一般包含字段：

- messages：消息列表（HumanMessage、AIMessage、ToolMessage）；
- query：原始用户问题；
- tools_called：已调用工具记录；
- intermediate_steps：中间思考与工具返回结果；
- final_answer：最终输出；
- error：异常信息。

> 面试重点：State是累加更新，不是覆盖，支持自定义Reducer合并数据。

### 8. Human-in-the-loop 是什么，在LangGraph怎么实现？

**答案** 人工介入，当Agent要执行高危操作（修改数据库、发邮件）时，暂停执行，交给人工审批，确认后再继续执行。

实现：在工具调用节点前加一个中断节点，`interrupt()`暂停图；人工输入确认信号后调用`resume()`恢复状态继续跑。

## 三、工具调用（Tool Calling）高频题

### 9. 大模型函数调用（Tool Calling）原理，两种实现方式

**答案** 工具调用：让模型识别任务，生成结构化工具名称+入参，而不是自由文本。

两种方案：

1. **原生Function Calling（OpenAI/通义千问等）**：模型原生支持输出结构化工具调用JSON，稳定性高，推荐优先使用。底层是模型在训练时学习工具schema格式。
2. **Prompt + OutputParser**：不依赖原生能力，在system prompt描述工具定义，要求模型输出固定格式JSON，再用正则/JsonOutputParser解析。缺点：容易格式错乱，需要加重试。

工具调用流程： 用户提问 → LLM判断需要调用工具 → 输出tool_name+arguments → 代码层执行工具拿到结果 → ToolMessage回传给LLM → LLM继续思考或输出答案。

### 10. 工具调用常见失败原因，怎么优化？

**答案** 常见问题：

1. 模型幻觉编造不存在的工具名；
2. JSON格式错误、缺少字段；
3. 参数类型错误（字符串写成数字）；
4. 工具描述写得太差，模型不知道什么时候该调用；
5. 上下文太长，模型忘记工具定义。

优化手段：

1. 精简工具描述，清晰写明适用场景；
2. 限制工具数量，不要一次性给几十个工具；
3. 加输出解析器+重试机制；
4. 用原生Function Calling替代纯Prompt方案；
5. 增加校验层：代码侧对入参做schema校验，非法参数直接返回错误给模型。

## 四、RAG & 向量数据库

### 11. RAG 完整链路，以及每个环节优化手段

**答案** 完整链路：文档加载 → 文档清洗 → 文本分块 → 向量化Embedding → 存入向量库 → 用户Query → Query向量化 → 相似度检索 → 召回文档 → 重排Rerank → 上下文组装 → LLM生成回答。

优化点：

- 分块：不要固定长度，用语义分块；保留段落上下文重叠；
- Embedding：选择领域适配的向量模型；
- 检索：Hybrid检索（向量+关键词BM25）；
- Rerank：召回Top20，Rerank筛选Top3，提升精度；
- Query改写：Query扩写、多子Query生成，解决歧义；
- 过滤：元数据过滤（时间、文档类型）。

### 12. 向量数据库原理，Qdrant / Chroma / Milvus 对比，选型依据

**答案** 向量库：存储向量Embedding，支持高维向量相似度检索（余弦相似度/欧氏距离），底层索引：HNSW最常用。

- Chroma：轻量，本地开发测试，不适合生产大数据量；
- Qdrant：轻量高性能，单机也能扛，支持payload过滤，Agent开发最常用；
- Milvus：分布式，海量向量，适合企业大规模知识库。

选型：开发测试用Chroma；中小规模生产选Qdrant；百万级以上向量、多节点分布式选Milvus。

### 13. RAG 存在哪些问题？怎么缓解幻觉？

**答案** RAG问题：检索偏差、召回无关文档、上下文窗口限制、文档冲突、幻觉。

缓解幻觉：

1. 提升检索质量（hybrid+rerank）；
2. Prompt约束：如果文档没有信息，直接回答不知道，禁止编造；
3. 引用溯源：输出答案附带文档来源ID；
4. 事实校验Agent：单独一个Agent校验生成结果和原文是否一致；
5. 降低温度（temperature）。

## 五、工程落地、稳定性、性能

### 14. Agent 系统会遇到哪些稳定性问题？如何保障生产可用？

**答案** 稳定性问题：

1. LLM服务超时、限流、返回格式异常；
2. 工具调用失败、第三方API报错；
3. Agent无限循环，反复调用同一个工具；
4. Token持续上涨，成本失控；
5. 并发请求导致向量库压力大；
6. 幻觉输出错误业务数据。

生产保障方案：

1. 熔断、重试、超时机制；
2. 设置最大迭代轮次，防止死循环；
3. Token计数，上下文截断；
4. 工具权限隔离，高危操作人工审批；
5. 日志埋点：记录每一步thought、action、observation；
6. 评估集：自动化评测Agent成功率；
7. 缓存：重复查询缓存LLM结果与检索结果。

### 15. Agent 评测怎么做？指标有哪些？

**答案** 两类评测：人工评测 + 自动评测。

指标：

1. 任务完成率（最核心）：能不能完成用户目标；
2. 工具调用准确率：是否在正确时机调用正确工具；
3. 幻觉率；
4. 步骤数：完成任务调用多少次工具（越少越好）；
5. Token消耗、耗时；
6. 回答忠实度（Faithfulness），参考RAGAS评测框架。

RAGAS：适合RAG；Agent可以自定义数据集，用LLM-as-judge做自动打分。

### 16. 什么是Agent死循环？如何避免？

**答案** Agent反复调用同一个工具，每次拿到相同结果，一直循环无法终止。

原因：

- 工具返回信息没有增量；
- LLM没有判断任务已经完成；
- 缺少终止条件。

解决方案：

1. 设置最大执行步数；
2. 在State记录已经调用过的工具+参数，避免重复调用；
3. Prompt明确：如果连续多次获取相同信息，停止调用；
4. 增加终止节点判断。

## 六、架构设计题（中高级必问）

### 17. 设计一个企业内部知识库Agent，简述整体架构

**答案** 分为离线预处理阶段 + 在线Agent服务阶段。

离线： 各类文档（PDF/Word/Markdown）→ 文档解析清洗 → 语义分块 → Embedding → Qdrant向量库，附带文档元数据。

在线服务： 用户请求接入层 → LangGraph Agent编排 Agent内部逻辑：

1. 接收用户问题；
2. 判断是否需要检索知识库；
3. 调用RAG工具（hybrid检索+rerank）；
4. 拿到文档；
5. LLM生成答案；
6. 校验答案是否来自文档；
7. 返回结果+引用来源。

额外能力：

- 记忆：向量长期记忆保存用户历史；
- 人工审批（如果涉及修改业务数据）；
- 监控日志、token统计；
- 限流熔断。

### 18. Agent 和微服务怎么结合？Agent调用业务接口有哪些注意事项？

**答案** Agent工具层封装为微服务接口，Agent只负责决策，业务逻辑仍然放在后端微服务，Agent不写业务。

注意事项：

1. 参数强校验，防止LLM构造恶意参数；
2. 权限控制，做好鉴权；
3. 接口超时、熔断；
4. 敏感操作强制人工审批；
5. 入参Schema严格定义，给LLM清晰的工具描述；
6. 记录完整审计日志。

## 七、Java方向额外面试题（如果你面试Java后端Agent岗位）

> 很多公司Java栈做Agent服务，用LangChain4j

### 19. LangChain4j是什么？和Python LangChain差异？

**答案** LangChain4j：Java生态的大模型应用开发框架，对标Python LangChain。提供ChatModel、Embedding、RAG、Agent、Tool Calling抽象。

差异： Python生态工具更丰富，LangGraph只在Python；LangChain4j适合集成Java微服务，在Java进程内直接开发Agent应用，不用跨语言调用。 LangChain4j Agent工具调用支持原生Function Calling，记忆、RAG组件齐全。缺点：生态组件少于Python版本。

### 20. Java开发Agent，如何处理LLM返回的JSON结构化数据？

**答案** 两种方式：

1. 使用LangChain4j的`@Tool`注解，定义Java方法，框架自动生成工具schema，原生function calling，自动序列化反序列化；
2. 自定义输出解析器，用Jackson做JSON解析，捕获解析异常，加入重试策略。

> 最佳实践：优先使用LangChain4j工具注解，减少手动解析JSON带来的稳定性问题。

## 八、开放思考题

### 21. Agent当前最大瓶颈是什么？

**答案**

1. 推理成本高，多轮Agent token消耗大；
2. 复杂任务规划能力弱，长任务容易跑偏；
3. 工具调用稳定性依赖大模型能力；
4. 很难保证100%可靠，不能直接用于高风险业务；
5. 难以评估，很难做全面自动化测试。

### 22. 多Agent是什么场景？多Agent协作模式

**答案** 多个Agent分工完成复杂任务，例如：检索Agent、校验Agent、写作Agent。 常见模式：

- 分工模式：主Agent调度多个子Agent；
- 辩论模式：多个Agent互相校验，降低幻觉；
- 路由模式：根据问题类型路由到专用Agent。

适合场景：复杂科研、长文档分析，不适合简单业务查询（多Agent成本太高）。
