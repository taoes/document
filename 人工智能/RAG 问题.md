## 一、整体架构设计

  

整个RAG系统采用**六层架构**，从上到下依次为：

  

```
┌─────────────────────────────────────────────────────────────────┐
│ 应用层（API / Web UI） │
├─────────────────────────────────────────────────────────────────┤
│ 问答生成层（LLM + Prompt） │
├─────────────────────────────────────────────────────────────────┤
│ 检索优化层（重排序 + 上下文压缩） │
├─────────────────────────────────────────────────────────────────┤
│ 索引与检索层（向量库 + 混合检索） │
├─────────────────────────────────────────────────────────────────┤
│ 文档处理层（解析 + 分块 + 向量化） │
├─────────────────────────────────────────────────────────────────┤
│ 数据源层（PDF / 网页 / 业务文档） │
└─────────────────────────────────────────────────────────────────┘
```

  

分层逻辑：数据自下而上流动，每一层解决一个核心问题——数据源层解决文档接入，文档处理层解决解析质量，索引检索层解决召回精度，检索优化层解决token溢出和幻觉，问答生成层解决最终答案质量。

  
  

## 二、文档处理流程（端到端）

  

### 第一阶段：文档接入与解析

  

**多源文档统一接入**：

- **PDF文档**：使用分层解析策略。简单PDF用PyMuPDF4LLM（速度>200页/分钟），含复杂表格、公式的用MinerU或Marker。MinerU对数学公式识别精准，适合科技/专利类文档。

- **网页内容**：使用BeautifulSoup提取正文，去除HTML标签、脚本和样式。

- **业务文档（Word/Excel等）** ：MarkItDown处理Word，Unstructured.io作为通用格式兜底。

  

**关键原则**：原始文档解析质量直接决定RAG系统上限，“垃圾进，垃圾出”（GIGO）在此绝对成立。企业级应用要求关键信息提取精度通常需≥95%。

  

**表格与图像处理**：

- 表格：DoclingAI专攻表格提取，精度可达98%以上

- 图像：采用三重索引机制——检索文本=原始文字+AI图片描述（向量化），LLM输入=纯净原始文本（避免描述污染），图像引用=URI存储（前端渲染）

  

### 第二阶段：文本清洗与规范化

  

- 结构化清洗：按文档类型分别处理——Markdown去除格式化符号、网页剥离HTML、PDF去除页面 artifacts

- 通用规范化：空白符归一化、换行清理、Unicode规范化、段落格式统一

  

### 第三阶段：智能分块（Chunking）

  

采用**语义分块**策略，根据文档长度动态调整：

- 短文档 → 较大分块

- 长文档 → 较小分块+重叠（overlap 10-20%），避免信息割裂

- 推荐文本块大小控制在200-500 token

  

### 第四阶段：向量化与索引

  

- 使用中文优化的Embedding模型（如BGE-large）

- 向量存储至FAISS或专业向量数据库

- 同时构建**关键词倒排索引**（BM25）支持混合检索

  

### 第五阶段：增量更新机制

  

文档持续更新时，采用**增量索引**策略：

- 新文档加入时，仅更新受影响的局部索引，无需全量重建

- 维护每个源文件的**版本清单**，用Tombstone（撤回标记）标记已失效版本

- 使用**版本水位**判断检索层是否已追上最新变更

- 文档变更时自动触发索引更新，无需手动干预

  
  

## 三、四大核心问题的解决方案

  

### 问题一：召回不准

  

**根因**：纯向量检索对精确术语（如产品型号、编号）召回差；纯关键词检索无法理解语义。

  

**解决方案——四层渐进式检索**：

  

**第一层：混合检索（Hybrid Search）**

- 同时执行**密集检索**（向量语义相似度）和**稀疏检索**（BM25关键词匹配）

- 两者优势互补：稀疏检索擅长精确术语匹配，密集检索擅长语义理解

- 融合打分：`score_hybrid = α·sim_vec + (1-α)·sim_bm25`

- 动态权重可根据查询类型自适应调整

  

**第二层：重排序（Reranking）**

- 初步检索召回Top-K候选（如50个），再用Cross-Encoder模型精排

- 重排序可显著提升召回质量。实验表明，使用RankLLaMA重排序可将MAP从0.523提升至0.797，相对提升52%

- bge-reranker-v2-m3等重排序器能显著提升复杂场景下的忠实度

  

**第三层：多样性去重（MMR）**

- 使用MMR（Maximal Marginal Relevance）算法，在保证相关性的同时增加内容多样性，减少冗余

  

**第四层：查询改写（Query Reformulation）**

- 对用户模糊查询进行多角度改写，生成多个查询变体分别检索后融合

  
  

### 问题二：大模型幻觉

  

**根因**：检索到的上下文不相关（“垃圾进，垃圾出”），或模型过度依赖自身参数知识而忽略检索证据。

  

**解决方案——五道防线**：

  

**防线一：提升检索质量（源头治理）**

- 上述“混合检索+重排序”方案确保送入LLM的上下文高度相关，从源头减少幻觉诱因

  

**防线二：证据性引导压缩（ECoRAG）**

- 在将上下文送入LLM前，基于**证据性**（evidentiality）对检索文档进行压缩，只保留能支撑答案生成的证据片段

  

**防线三：多智能体辩论（DRAG）**

- 引入Multi-Agent Debate机制，多个智能体对检索结果和生成答案进行交叉验证，减少RAG-induced幻觉

  

**防线四：忠实度验证（Faithfulness Verifier）**

- 生成答案后，用验证模块检查答案中的每个事实是否能在检索上下文中找到依据

- 无法验证的陈述自动标记或拒绝回答

  

**防线五：降低模型温度**

- 将LLM温度参数调低（如0.1），减少创造性回答，提高事实性

  
  

### 问题三：上下文Token溢出

  

**根因**：检索返回多个文档块，拼接后远超模型上下文窗口限制；即使窗口够大，长上下文会导致注意力稀释和性能下降。

  

**解决方案——三层压缩策略**：

  

**第一层：自适应检索数量（Adaptive-k）**

- 传统RAG固定检索前k个文档，不考虑查询复杂度

- Adaptive-k根据查询与候选文档的**相似性分布间隙**动态确定最优检索数量

- 事实性查询只需少量文档，聚合性查询需要更多证据

  

**第二层：智能上下文压缩（REFRAG）**

- Meta提出的REFRAG框架：将检索到的长文档切成固定大小的块，每个块经轻量级编码器压缩为embedding

- 压缩后输入长度缩短k倍，显著减少注意力计算

- 同时用强化学习策略动态决定哪些关键块保留原始token（不压缩），保证信息完整

- 实测效果：30.85倍TTFT加速，上下文处理长度扩展16倍

  

**第三层：选择性证据组装**

- 在固定上下文预算内，用“替换而非扩展”的策略组装最相关的证据片段

- 在3%的压缩比下，不仅避免性能下降，还能提升平均EM分数3.3分

  
  

### 问题四：文档持续更新

  

**根因**：静态索引无法感知源文档变化，导致回答过时信息。

  

**解决方案——版本化增量索引**：

  

**机制一：文档版本管理**

- 为每个源文档维护**版本化清单**，每次更新产生新版本号

- 每个索引块关联明确的文档标识符和修订状态

  

**机制二：变更触发更新**

- 文档变更时（新增/修改/删除），自动触发增量索引更新

- 使用Change Streams或Webhook监听数据源变化

  

**机制三：旧知识失效机制**

- 使用Tombstone（撤回标记）标记已删除或已过时的文档版本

- 检索时通过**版本水位**（version watermark）过滤，确保只召回最新版本

- 旧版本可选择保留作为历史参考，但默认被元数据过滤排除

  

**机制四：热加载无停机更新**

- 新索引分区向量库热加载，无需重启服务

- 检索接口毫秒级感知新知识

  
  

## 四、技术选型速查表

  

| 环节 | 推荐方案 | 备选方案 |

|------|---------|---------|

| PDF解析 | MinerU / PyMuPDF4LLM | Marker（含公式） |

| 网页解析 | BeautifulSoup | 无 |

| 通用格式 | Unstructured.io | 无 |

| 分块策略 | 语义分块（200-500 token, 10-20% overlap） | 递归字符分块 |

| 向量模型 | BGE-large（中文优化） | EmbeddingGemma |

| 向量数据库 | FAISS / Milvus | Pinecone / Qdrant |

| 混合检索 | BM25 + 向量检索（QueryFusionRetriever） | 单独检索后融合 |

| 重排序 | bge-reranker-v2-m3 / RankLLaMA | Cross-Encoder |

| 上下文压缩 | REFRAG / ECoRAG | SARA |

| 增量索引 | CocoIndex / 自建版本水位机制 | 定时全量重建 |

  

## 五、总结

  

这套架构的核心思想是**分层治理**：文档处理层保障数据质量（解决GIGO），检索层通过混合检索+重排序提升召回，生成前通过上下文压缩控制token，生成后通过忠实度验证防幻觉，版本化增量索引保证知识新鲜度。四个问题不是孤立解决的，而是通过整个管道协同优化——**检索质量提升本身就在减少幻觉**，**上下文压缩保证了即使长文档也能高效处理**，**增量索引确保了答案时效性**。
