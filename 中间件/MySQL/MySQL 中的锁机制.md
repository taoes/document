# MySQL锁高频面试题（InnoDB，默认RR隔离级别，面试向，包含原理、踩坑、真实场景）

> 重点：共享锁S、排他锁X、意向锁、记录锁、间隙锁、临键锁、MVCC、死锁、锁降级/升级、加锁规则、锁失效场景

  

## 基础概念题

### Q1：InnoDB有哪些锁分类？

**回答要点**

1. **按粒度分**

- 表级锁：表共享读锁（table read lock）、表排他写锁（table write lock）、**意向共享IS、意向排他IX**（意向锁，InnoDB内部，解决表锁与行锁冲突检测）

- 行级锁（InnoDB核心）：共享S锁、排他X锁，锁的是索引，不是数据行。

2. **按锁算法（RR可重复读下）**

- 记录锁 Record Lock：锁索引上某一条确定记录

- 间隙锁 Gap Lock：锁索引间隙，防止幻读，锁住不存在的数据

- 临键锁 Next‑Key Lock = 记录锁 + 间隙锁，RR默认行锁算法

  

> 重要：**行锁是加在索引上，如果没有索引，行锁退化为表锁！**

  

---

  

### Q2：S共享锁、X排他锁，兼容矩阵是什么？

| 已持有\请求 | S共享锁 | X排他锁 |
|---|---|---|
| S | ✅兼容 | ❌互斥 |
| X | ❌互斥 | ❌互斥 |

  

- select … lock in share mode：加S共享锁；多个事务可以同时S锁；有事务加X锁就阻塞。

- select … for update：加X排他锁。

- DML(insert/update/delete) 内部自动加X排他锁。

  

> 注意：普通select快照读不加锁，走MVCC。

  

### Q3：意向锁 IS / IX 是干嘛的？为什么需要意向锁？

**参考答案**

意向锁是InnoDB表级锁，由InnoDB自动加，用户不能手动干预。

- IS：事务打算给表中行加S锁

- IX：事务打算给表中行加X锁

  

作用：快速判断「表锁」和「行锁」是否冲突。

> 举例：一个事务给某行加了行X锁（此时表上会带上IX意向排他锁）；另一个执行 `lock tables … write` 想要加表排他锁。

如果没有意向锁，数据库要遍历表里面每一行，判断有没有行锁，效率极低。

有了意向锁：直接判断表上意向锁和表锁是否冲突，不用扫描行。

  

兼容：IS和IX互相兼容；IS/IX和表X锁互斥。

  

> 坑：意向锁之间全部互相兼容，意向锁**不阻止其他事务加行锁**。

  

## 高频难点：临键锁、间隙锁、幻读（RR级别）

### Q4：什么是幻读？InnoDB RR隔离级别怎么解决幻读？

1. 幻读：同一个事务内，多次同样select，范围查询返回行数发生变化，出现之前不存在的行。

2. RR下解决幻读依靠 **Next‑Key临键锁（间隙锁+记录锁）**，锁住间隙，阻止其他事务insert新数据；

> ⚠️MVCC快照读不能解决幻读；**只有当前读（加锁读）靠临键锁防止幻读**。

> 快照读普通select，依然可以看到别的事务新插入的数据。

  

### Q5：临键锁、记录锁、间隙锁什么时候触发？加锁规则？

> 前提：RR隔离级别，B+树索引

1. 查询命中**唯一索引，精确匹配到存在记录** → 退化成**记录锁**，不加间隙锁。

2. 查询**唯一索引，但是没有命中记录** → 使用间隙锁。

3. **普通二级索引，精确匹配**，不会退化成记录锁，会加临键锁，包含间隙锁。

4. **范围查询（> < >= <=）**，会加临键锁。

  

示例：索引值 `10,20,30`

next‑key锁区间：`(-∞,10], (10,20], (20,30], (30,+∞]`

  

> 面试坑：普通索引即便是等值查询，也会带间隙锁，会锁住左右间隙，容易导致大量锁等待。

  

### Q6：RC 和 RR隔离级别锁的区别？

1. RC（读提交）：**没有间隙锁、没有临键锁，只有记录锁**；会出现幻读；锁粒度更小，并发更好。

2. RR（可重复读）：默认，存在间隙锁、临键锁，解决当前读幻读，但更容易锁范围过大，产生锁等待。

  

> 很多业务会调为RC，牺牲幻读，换取更高并发。

  

## 死锁高频题

### Q7：InnoDB死锁产生条件，怎么定位死锁，怎么避免死锁？

死锁4条件：互斥、持有并等待、不可剥夺、循环等待。

  

**定位死锁**

```sql
show engine innodb status;
```

看 `LATEST DETECTED DEADLOCK` 段，里面记录两个事务锁、执行SQL、等待的锁资源。

  

**常见死锁场景**

场景1：两个事务更新行顺序相反。

> T1 update set a=? where id=1; 再去更新id=2

> T2 update set a=? where id=2; 再去更新id=1，循环等待造成死锁。

  

场景2：间隙锁造成的死锁（RR下很常见），多个事务向同一个间隙插入。

  

**避免死锁方案**

1. 多个行更新，**统一访问行的顺序**；

2. 业务尽量避免大事务，缩小事务执行时间；

3. RC隔离级别关闭间隙锁，减少死锁概率；

4. 控制不要一次性锁住过多资源；

5. InnoDB检测死锁之后，会代价回滚较小的事务。

  

### Q8：update没走索引，会发生什么？

> update/delete where条件没有索引，**行锁退化为表级X锁，整个表被锁住，其他所有DML全部阻塞**。生产重大事故来源。

> 排查：explain看type，如果ALL全表扫描，要警惕锁表风险。

  

## 当前读 vs 快照读（非常高频）

### Q9：快照读、当前读区别？

- **快照读（普通select）**：基于MVCC read‑view，读取历史版本，不加锁；不加锁，并发高。

`select * from t;`

  

- **当前读，加锁读**：读取最新版本，加行锁

`select ... for update / lock in share mode`

`update / delete / insert`

  

> 面试坑：RR下，快照读不会被行锁阻塞，只有当前读才会被锁阻塞。

  

### Q10：MVCC实现原理？undo log、read view作用？

MVCC只作用快照读。

1. undo log：保存数据旧版本链，数据修改不直接覆盖，旧版本放undo log；

2. read‑view：事务开启时生成，用来判断版本链中哪个版本对当前事务可见；

3. trx_id、roll_pointer，每行隐藏列。

  

> MVCC解决读写不阻塞，但是**MVCC不处理写‑写冲突，写‑写冲突依旧靠行锁解决**。

  

## 锁等待、锁超时

### Q11：lock wait timeout 是什么？和死锁区别？

- `lock wait timeout exceeded`：锁等待超时，事务拿不到锁，等待时间超过参数 `innodb_lock_wait_timeout`（默认50秒）抛出异常；**不是死锁，只是拿不到锁**。

- 死锁：循环等待，InnoDB主动检测，立刻回滚其中一个事务。

  

排查锁等待：

```sql

select * from information_schema.innodb_trx; --运行中的事务

select * from information_schema.innodb_locks;

select * from information_schema.innodb_lock_waits;

```

  

## 真实业务面试题（面试官最爱问）

### Q12：线上遇到大量锁等待，排查思路？

1. 看报错：死锁还是lock wait超时；

2. `show engine innodb status`，查看锁信息；

3. 查看innodb_trx，找到长时间没提交的大事务（大事务持有锁不放是头号元凶）；

4. explain检查SQL，确认where条件是否命中索引，防止行锁退化表锁；

5. 分析SQL加锁范围：是不是临键锁间隙锁锁了过大范围；

6. 业务层面：拆分大事务，减少事务持有锁时间；评估是否切换RC隔离级别消除间隙锁。

  

### Q13：select for update有哪些坑？

1. 条件无索引，锁整张表；

2. RR级别普通索引等值查询，会带间隙锁，锁住间隙，其他insert阻塞；

3. for update 如果查询不到数据，依然会加间隙锁，阻塞插入；

4. 高并发大量for update，容易锁等待；

5. 注意：mysql8.0支持 `select ... for update skip locked / nowait`，跳过锁等待，业务防超卖场景常用。

  

> skip locked：拿不到锁直接跳过这行；nowait拿不到锁直接报错。

  

### Q14：业务防超卖，用select for update有什么问题？有没有替代方案？

问题：高并发行锁竞争，数据库压力大。

方案：

1. 数据库乐观锁：version版本号 update set stock=stock‑1,version=version+1 where id=xx and version=old_version;

2. Redis预扣库存，异步落库；

3. 业务层限流。
