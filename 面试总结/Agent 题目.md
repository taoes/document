## 一、推理框架

### CoT（思维链）

**Q1：CoT 为什么能提升推理能力？在什么条件下 CoT 才会涌现？**

CoT 的核心机制是将隐式的推理过程外显化，让模型在生成最终答案前先展开中间步骤。这相当于把一次"跳跃式"输出分解为多个条件概率的连乘，每一步的生成都以前一步为条件，降低了单步预测的复杂度。CoT 的涌现与模型规模强相关——论文实验表明，当模型参数量达到约 100B 量级时，CoT 才开始显著超越标准 prompting，小模型使用 CoT 甚至可能因产生错误推理链而降低性能。

**Q2：Zero-shot CoT 和 Few-shot CoT 有什么区别？**

Zero-shot CoT 仅需在 prompt 末尾追加"Let's think step by step"，无需提供示例，泛化性好但推理质量不稳定。Few-shot CoT 提供若干"问题→推理步骤→答案"的完整示例，通过 in-context learning 引导模型模仿推理格式，在复杂任务上更可靠，但示例的选择和数量对效果影响大，且增加了 token 开销。

**Q3：CoT 的局限性是什么？什么时候 CoT 反而会降低性能？**

局限性包括：
- ① 推理链中的错误会逐步累积（误差传播）；
-  ② 对简单事实性问答无益甚至有害，因为引入不必要的中间步骤可能产生幻觉；
- ③ 计算成本线性增加；④ 无法与外部环境交互，纯粹"纸上谈兵"。当任务不需要多步推理（如简单分类、直接检索）时，CoT 可能因引入噪声而降低准确率。

**Q4：Auto-CoT 怎么实现？**

Auto-CoT 通过自动化方式生成高质量的 CoT 示例。核心思路是：先用 Zero-shot CoT 让模型对一批问题生成推理链，再通过聚类选择多样化的示例，或通过一致性过滤剔除错误推理链，最终得到无需人工标注的 few-shot 示例集。

### ReAct

**Q5：ReAct 和纯 CoT 的核心区别是什么？ReAct 怎么解决幻觉问题？**

CoT 只在"思维空间"内推理，不接触外部信息，因此容易产生事实性幻觉。ReAct 将推理（Thought）与行动（Action）交错进行，每一步行动后获取环境反馈（Observation），再基于真实观察继续推理。幻觉的缓解机制在于：当模型的推理与外部工具返回的事实不一致时，Observation 会"打断"错误推理链，迫使模型修正方向。ALFWorld 成功率提升 34%，WebShop 提升 10%，验证了外部 grounding 的有效性。

**Q6：手写一个 ReAct 循环，如何处理 Action 失败？**

```python
def react_loop(llm, tools, query, max_steps=10):
    messages = [{"role": "user", "content": query}]
    for step in range(max_steps):
        response = llm.chat(messages, tools=tools)
        messages.append(response)
        if response.tool_calls:
            for tool_call in response.tool_calls:
                try:
                    result = execute_tool(tools, tool_call)
                except Exception as e:
                    result = {"error": str(e), "suggestion": "检查参数格式"}
                messages.append({
                    "role": "tool",
                    "tool_call_id": tool_call.id,
                    "content": json.dumps(result)
                })
        else:
            return response.content
    return "Max steps reached"
```

处理 Action 失败的关键：① 将错误信息作为 Observation 返回给模型，让它有机会重试或换工具；② 设置单步重试上限（如连续 2 次失败则跳过）；③ 在 tool schema 中明确参数约束，从源头减少失败。

**Q7：ReAct 的最大步数限制怎么设？如何判断 Agent 陷入死循环？**

最大步数通常设为 10–20 步，具体取决于任务复杂度。死循环的检测方法：① 监测连续多步的 Thought/Action 是否高度重复（如编辑距离低于阈值）；② 检查工具调用参数是否与之前相同；③ 监控 Observation 是否长时间无实质变化；④ 设置 token 预算上限，超限即终止。

**Q8：ReAct 和 Function Calling 的关系是什么？可以结合使用吗？**

ReAct 是一种推理-行动范式，Function Calling 是实现"行动"的底层机制。ReAct 循环中的 Action 步骤，在现代 LLM 中通常通过 Function Calling 接口来结构化输出工具调用请求。二者是"框架"与"工具"的关系，完全可以结合——文章中的 ReAct 循环代码正是使用 `response.tool_calls` 来解析 Action 的。

### ToT（思维树）

**Q9：ToT 和 CoT 的本质区别是什么？**

CoT 是线性链式推理，每条推理路径只有一条分支，无法回溯。ToT 将推理过程建模为树状搜索，每个节点是一个"思维"（thought），允许从多个候选分支中选择、评估和回溯。本质区别是搜索空间的结构：CoT 是 depth-only 的线性遍历，ToT 在宽度和深度两个维度上同时探索。

**Q10：ToT 中 BFS 和 DFS 搜索策略怎么选择？**

BFS 适合需要全局最优解的任务（如 Game of 24），每层保留 top-k 个候选状态，避免过早陷入局部最优，但内存开销大。DFS 适合深度优先的规划任务，内存友好但可能错过更优路径。选择依据：任务是否需要"全局比较"——如果需要从多个完整方案中择优，选 BFS；如果任务有明确的深度方向（如逐步推导），选 DFS。

**Q11：什么场景下该用 ToT 而不是 CoT？ToT 的计算成本怎么控制？**

适合 ToT 的场景：① 解空间大且存在多条可行路径（数学证明、谜题求解）；② 需要自我评估和回溯的任务（Game of 24、创意写作）。成本控制手段：限制分支因子（每层候选数 ≤ 3–5）、限制深度、使用轻量模型做评估节点、对中间状态做剪枝。

## 二、Agent 架构

### 记忆系统

**Q12：请设计一个 Agent 的记忆系统，包括短期记忆和长期记忆**

- 短期记忆：维护当前会话的上下文窗口，采用滑动窗口 + 摘要压缩策略——最近 N 轮保留原文，更早的轮次压缩为摘要。
- 长期记忆：使用向量数据库存储跨会话的"经验条目"，每条记忆包含内容、时间戳、重要性评分和访问频率。检索时采用混合检索（向量相似度 + 时间衰减 + 重要性加权）。写入策略：对话结束后，由 LLM 判断哪些信息值得长期存储，生成反思性摘要后入库。

**Q13：上下文窗口溢出了怎么办？摘要压缩和滑动窗口各有什么问题？**

摘要压缩的问题：信息丢失不可逆，压缩后的摘要可能遗漏关键细节；摘要本身可能引入 LLM 的幻觉。滑动窗口的问题：被移出窗口的早期信息完全不可访问，对于需要跨轮次引用的任务（如多轮工具调用）会造成上下文断裂。更优方案是分层记忆：近期原文 + 中期摘要 + 长期向量检索，按需召回。

**Q14：长期记忆怎么避免"记忆污染"？**

关键措施：① 写入前做事实性校验（用检索工具验证）；② 为每条记忆维护置信度分数，低置信度记忆在检索时降权；③ 实现记忆的"遗忘机制"——长期未被访问且置信度低的记忆逐步淘汰；④ 支持人工修正和删除接口。

**Q15：向量检索、关键词检索、混合检索怎么选择？**

向量检索适合语义匹配（同义表述、模糊查询），但对精确术语和稀有词不敏感。关键词检索（BM25）适合精确匹配和稀有词，但无法处理语义泛化。混合检索结合两者，通常采用 RRF（Reciprocal Rank Fusion）融合排名，是 RAG 系统中最稳妥的选择。选择依据：如果查询中包含大量专有名词和编号，必须加关键词检索；如果用户表达高度口语化，向量检索权重应提高。

**Q16：Generative Agents 中的 Reflection 机制怎么工作？**

斯坦福小镇实验中的 Reflection 机制：Agent 定期（如每天结束时）将短期记忆中的观察记录输入 LLM，生成更高层次的"洞察"（insights）。这些洞察以自然语言形式存储为长期记忆条目，并在后续决策中通过检索被召回。核心流程是：观察 → 记忆存储 → 反思（生成洞察）→ 检索 → 规划，反思使 Agent 能够从具体经历中抽象出行为模式。

### 规划（Planning）

**Q17：Agent 的 Planning 能力怎么实现？有哪些主流方法？**

主流方法包括：① **ReAct 式**：不预先规划，边推理边决定下一步（反应式规划）；② **Plan-and-Execute**：先由 LLM 生成完整的多步计划，再逐步执行，执行中可动态修正；③ **LLM Compiler**：将规划建模为 DAG，支持并行执行；④ **Tree Search 式**：用 ToT 或 MCTS 在规划空间搜索最优路径。选择依据：任务不确定性低时用 Plan-and-Execute，不确定性高时用 ReAct。

**Q18：多步任务的子目标分解怎么做？怎么处理规划失败？**

子目标分解：使用 LLM 将高层目标拆解为可执行的子任务序列，每个子任务应有明确的完成条件和输入输出。处理规划失败：① 执行失败时将错误信息回传给规划器，重新生成子计划；② 设置"规划-执行-反思"循环，每执行 K 步后评估进度是否偏离；③ 保留回退点，失败时回退到上一个成功状态。

**Q19：Human-in-the-loop 的介入时机怎么设计？**

介入时机设计原则：① **高风险操作前**：如资金转账、数据删除、外部通信，必须人工确认；② **低置信度时**：当 Agent 的决策置信度低于阈值（如 < 0.7）时转人工；③ **规划阶段**：对于多步任务，在生成计划后请求人工审批；④ **异常检测**：检测到操作序列异常（如短时间内大量工具调用）时暂停。

### 行动（Action）

**Q20：Agent 调用工具失败了怎么优雅降级？**

降级策略分层：① 重试（指数退避 + 最大次数）；② 切换备用工具（如主 API 挂了切到备用 API）；③ 降级为"告知用户当前无法完成该操作，但可以继续完成其他部分"；④ 回退到规则引擎执行确定性逻辑；⑤ 如果所有工具都失败，将错误上下文返回给 LLM，让它生成用户友好的解释和建议。

**Q21：多工具并行调用怎么实现？如何处理工具间的依赖关系？**

并行调用：在 ReAct 循环中，当 LLM 一次返回多个 tool_calls 时，使用 `asyncio.gather` 或线程池并行执行，结果按 tool_call_id 聚合。依赖关系处理：在工具定义中增加 `depends_on` 字段，调度器先构建依赖图，对无依赖的工具并行执行，对有依赖的工具按拓扑序串行执行。

**Q22：Computer Use Agent 的技术挑战有哪些？**

三大挑战：① **屏幕理解**：截图分辨率高、UI 元素密集，视觉模型需要精确定位可操作元素；② **元素定位**：将自然语言指令映射到屏幕坐标（如"点击登录按钮"→ 坐标），需要 GUI grounding 能力；③ **操作序列规划**：GUI 操作是长序列、状态不可逆的，需要处理弹窗、加载、错误提示等动态情况。评估基准包括 WebArena 和 OSWorld。

## 三、工具与协议

### Function Calling

**Q23：Function Calling 的 JSON Schema 怎么设计？嵌套参数怎么处理？**

JSON Schema 应包含 `name`、`description`、`parameters`（遵循 JSON Schema 规范）。关键设计原则：description 要写清楚"什么时候用"和"参数含义"；参数类型尽量简单（避免深层嵌套）；必填参数用 `required` 声明。嵌套参数使用 `type: "object"` + `properties` 递归定义，但深度建议不超过 2–3 层，否则模型容易生成错误结构。

**Q24：工具描述写得好不好直接影响调用准确率，你怎么优化工具描述？**

优化策略：① 在 description 中包含**使用场景**（"当用户询问天气时调用"）和**不适用场景**（"不要用于查询历史天气"）；② 参数描述要具体（"城市名，如'北京'，不要传省份"）；③ 提供 few-shot 示例（在工具定义中或 system prompt 中）；④ 使用负例说明（"此工具不处理国际天气"）。

**Q25：并行 Function Calling 怎么实现？错误重试策略？**

实现：LLM 单次响应返回多个 `tool_calls`，框架并行执行后按 id 回填。错误重试：① 对可重试错误（超时、限流）使用指数退避（1s → 2s → 4s）；② 对不可重试错误（参数错误、权限不足）不重试，直接将错误信息作为 Observation 返回；③ 设置总重试预算，避免无限循环。

### MCP（Model Context Protocol）

**Q26：MCP 解决了什么问题？和 Function Calling 的关系是什么？**

MCP 解决的是**工具生态碎片化**问题：在 MCP 之前，每个 Agent 框架都有自己的工具接入方式，开发者需要为不同框架重复适配。MCP 提供了标准化的工具描述和调用协议，使工具可以跨框架复用。与 Function Calling 的关系：Function Calling 是**模型层面**的工具调用能力，MCP 是**工程层面**的标准化协议——MCP Server 暴露的工具最终仍然以 Function Calling 的形式被模型调用。

**Q27：MCP 的三种原语分别是什么？怎么用？**

三种原语：① **Resources**：只读数据源（如文件、数据库查询结果），Agent 可以请求读取；② **Tools**：可执行操作（如发送邮件、创建工单），Agent 调用后产生副作用；③ **Prompts**：预定义的提示模板，帮助 Agent 以标准化方式使用工具。使用方式：MCP Client（Agent 端）连接 MCP Server，Server 在初始化时声明自己提供的 Resources/Tools/Prompts，Client 将其转换为 Function Calling 的 tool schema。

**Q28：如何设计一个 MCP Server？安全考量有哪些？**

设计要点：① 清晰定义工具边界（每个工具做一件事）；② 使用 JSON Schema 描述参数；③ 实现健康检查和优雅关闭。安全考量：① 认证授权（OAuth 2.0 或 API Key）；② 输入校验（防止注入）；③ 操作审计日志；④ 敏感操作的二次确认；⑤ 网络隔离（Server 不直接暴露公网）。

**Q29：MCP 的远程连接和 OAuth 授权怎么实现？**

远程连接：MCP 支持 SSE（Server-Sent Events）和 Streamable HTTP 两种传输方式，Client 通过 HTTP 长连接接收 Server 的推送。OAuth 实现：Server 作为 OAuth Resource Server，Client 携带 Bearer Token 访问；Token 通过标准 OAuth 2.0 授权码流程获取，MCP 规范定义了 Resource Indicators 来标识目标资源。

### A2A（Agent-to-Agent Protocol）

**Q30：A2A 和 MCP 的区别？为什么需要两个协议？**

MCP 解决的是 **Agent ↔ 工具** 的通信标准化，A2A 解决的是 **Agent ↔ Agent** 的通信标准化。区别在于交互模式：MCP 是"请求-响应"式的工具调用，A2A 支持更复杂的多轮协商、任务委托和状态同步。需要两个协议是因为二者解决不同层次的问题——MCP 让 Agent 能调用外部能力，A2A 让多个 Agent 能协作完成复杂任务。

**Q31：Agent Card 怎么描述一个 Agent 的能力？**

Agent Card 是 A2A 中描述 Agent 能力的元数据，通常包含：Agent 名称和描述、支持的技能（skills）、输入/输出格式、认证要求、端点 URL 等。它类似于 MCP 中的 tool schema，但描述的是"一个 Agent 能做什么"，而非"一个工具能做什么"。Agent Card 通过 `/.well-known/agent.json` 端点暴露。

**Q32：跨框架 Agent 互操作的技术挑战是什么？**

挑战包括：① **消息格式不统一**：不同框架的 Agent 消息结构不同，需要协议层做转换；② **状态语义差异**：任务的"进行中/完成/失败"在各框架中定义可能不同；③ **认证与信任**：跨组织 Agent 调用需要建立信任链；④ **错误传播**：一个 Agent 的失败如何在协作链中传递和恢复。

## 四、系统设计题

**Q33：设计一个多 Agent 协作的客户服务系统**

架构：**路由 Agent**（意图分类）→ **专业 Agent**（退款/技术支持/账户）→ **升级 Agent**（复杂问题）。共享上下文通过会话状态存储（Redis）实现，对话摘要跨 Agent 传递。降级策略：专业 Agent 超时或置信度低时，回退到规则引擎处理。Human-in-the-loop：退款金额超过阈值、技术问题涉及数据安全时强制转人工。

**Q34：设计一个 RAG 系统，支持大规模文档库**

文档处理：语义切分（按段落/章节）优于固定长度切分。检索：混合检索（向量 + BM25）+ Reranking（Cross-Encoder）。生成：带引用溯源的 prompt，要求标注来源段落编号。评估：Recall@K、MRR 衡量检索质量，Faithfulness 和 Relevance 衡量生成质量。

**Q35：设计一个支持工具调用的 Agent 框架**

核心组件：**工具注册中心**（JSON Schema + 版本管理）→ **调度器**（依赖分析 → 并行执行 → 结果聚合）→ **安全层**（权限白名单 + 沙箱 + 审计）→ **重试策略**（指数退避 + 最大次数）。工具调用链路的可观测性通过 Trace ID 贯穿。

**Q36：设计 Agent 的可观测性系统**

关键要素：① 完整的 Thought-Action-Observation 链路追踪；② 指标采集：任务成功率、工具调用频次、Token 消耗、延迟 P99；③ 工具选型：LangSmith / LangFuse / Phoenix；④ 错误回放：记录完整上下文，支持按 Trace ID 复现。

**Q37：设计一个 Computer Use Agent**

流水线：截图 → 视觉模型理解 → 元素定位 → 操作规划 → 鼠标键盘执行。安全机制：危险操作（删除、支付）二次确认，操作前校验当前屏幕状态。评估：WebArena / OSWorld 基准。

## 五、编码实现题

**Q38：手写 ReAct 循环中，如何防止 Agent 陷入死循环？**

参考 Q6 的代码框架，防死循环措施：① 设置 `max_steps`（建议 10–15）；② 在每步检查 Thought/Action 是否与最近 2–3 步高度相似，相似则强制终止或注入提示；③ 监控工具调用参数的重复模式；④ 设置总 token 预算，超预算即终止并返回部分结果。

**Q39：RAG Pipeline 的 Chunking 策略怎么选择？固定长度 vs 语义切分各有什么优劣？**

固定长度切分：实现简单、chunk 大小均匀，但可能切断语义完整的段落，导致检索时上下文不完整。语义切分：按段落/章节/主题切分，保持语义完整性，检索质量更高，但 chunk 大小不一，可能产生过长的 chunk 超出 embedding 模型输入限制。实践建议：语义切分为主，对过长 chunk 做二次固定长度切分，并设置 overlap（如 10–20%）。

**Q40：如何实现流式输出（SSE）？异步工具调用怎么处理？**

SSE 实现：使用 `sse-starlette` 或 FastAPI 的 `StreamingResponse`，将 LLM 的 token 流逐块推送给前端。异步工具调用：在流式生成过程中，当检测到完整的 tool_call 时，将其放入 asyncio 队列，由独立协程执行；工具执行结果通过另一个 SSE 事件推送（如 `event: tool_result`），不阻塞主生成流。

## 六、安全、可控性与评估

**Q41：Prompt Injection 攻击的原理是什么？怎么防御？**

原理：攻击者将恶意指令嵌入到 Agent 会读取的外部内容中（如网页、文档、邮件），当 Agent 将该内容作为上下文处理时，恶意指令可能覆盖原始 system prompt。防御：① **指令隔离**：将外部内容标记为"不可信数据"，与 system prompt 明确分隔；② **输入净化**：过滤常见注入模式；③ **权限最小化**：Agent 对外部内容触发的操作进行权限限制；④ **输出校验**：对 Agent 生成的工具调用做白名单校验。

**Q42：Agent 如何防止被诱导执行危险操作？**

措施：① 危险操作白名单/黑名单（如禁止 `rm -rf`）；② 沙箱执行（文件系统、网络隔离）；③ 操作前二次确认（对高影响操作要求人工审批）；④ 意图校验（用独立模型判断当前操作是否与用户原始意图一致）；⑤ 速率限制（防止短时间内大量危险调用）。

**Q43：Human-in-the-loop 的介入时机怎么设计？哪些操作必须人工确认？**

必须人工确认的操作：资金交易、数据删除/修改、对外通信（发邮件/发消息）、系统配置变更、涉及个人隐私数据的操作。介入时机设计参见 Q19。

**Q44：如何防止 Agent 的"目标漂移"？**

目标漂移指 Agent 在多步执行中逐渐偏离原始目标。防护：① 每步执行后与原始目标做一致性检查（用 LLM 判断当前动作是否服务于原目标）；② 设置检查点，定期回顾原始指令；③ 限制单次任务的最大步数和最大 token 消耗；④ 在多 Agent 系统中，由独立的"监督 Agent"持续校验。

**Q45：Agent 的护栏怎么实现？规则约束 vs 模型判断？**

规则约束：确定性高、可解释，但覆盖不全（无法枚举所有危险模式）。模型判断：灵活、泛化好，但可能被绕过。实践建议**分层护栏**：第一层规则（正则/关键词/白名单）做快速拦截，第二层模型判断（用 fine-tuned 分类器或 LLM-as-Judge）做语义级检测，第三层人工抽检。

**Q46：Agent 的评估框架有哪些？各测什么？**

AgentBench：多环境 Agent 能力综合评估（操作系统、数据库、知识图谱等 8 个环境）。WebArena：Web 导航和操作能力。SWE-bench：软件工程任务（代码修复）评估。选择依据：根据 Agent 的应用场景选择对应基准。

**Q47：如何评估 RAG 系统的检索质量？Faithfulness 和 Relevance 怎么量化？**

检索质量：Recall@K（前 K 个结果中相关文档的召回率）、MRR（首个相关结果的排名倒数均值）、NDCG。Faithfulness：生成的答案是否忠实于检索到的文档，用量化方法——将答案拆解为原子声明，逐条验证是否有文档支撑，计算支持比例。Relevance：答案与问题的相关程度，可用 LLM-as-Judge 打分或 BERTScore 计算语义相似度。

**Q48：LLM-as-Judge 的方案怎么设计？有什么偏见问题？**

方案：用强模型（如 GPT-4）作为评估器，给定问题、参考答案和模型输出，让评估器按维度（准确性、完整性、有用性）打分。偏见问题：① **位置偏见**（倾向于选择靠前的选项）；② **长度偏见**（倾向于更长的回答）；③ **自我偏好**（倾向于同系列模型的输出）；④ **格式偏见**（对 markdown 格式回答打分更高）。缓解：随机化选项顺序、控制长度差异、使用多评估器投票。
